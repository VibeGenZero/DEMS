# Discord integration — what DEMS does in Discord

> TL;DR: The bot announces events (Components V2 container in the event colour with line-up, slot buttons and "Anmelden"/"Zum Event"; a discussion thread per event), lets members register through a modal, offers `/events`, `/register` (German client: `/anmelden`, registers in Discord like the buttons) `/unregister` (`/abmelden`) and `/my-events` (`/meine-events`, own upcoming registrations with „Abmelden“, „Slot wechseln“, „Zum Event“), sends DMs for every registration change, assigns/removes an event role, optionally creates private voice/text channels per event, and can create native Discord scheduled events. Everything targets ONE guild (`DISCORD_GUILD_ID`). The helpers named below live in the area modules of `bot/` (table in [bot](../modules/bot.md)) and are exported through `bot.js`.

## Discord application setup

- OAuth2 redirect: `${BASE_URL}/auth/discord/callback`; scopes for users: `identify guilds guilds.members.read`.
- Bot scopes: `bot applications.commands`. The bot logs its invite URL with the needed permissions on startup (`logBotInviteUrl` → `buildBotInviteUrl`, list with reasons in `utils/botPermissions.js` `BOT_PERMISSIONS`): ManageRoles, ManageChannels, SendMessages, SendMessagesInThreads, EmbedLinks, MentionEveryone, ViewChannel, ReadMessageHistory, UseExternalEmojis, Connect, CreateEvents, CreatePublicThreads (B-14).
- Discord lets a bot grant only permissions it has itself: everything `addParticipantToEventChannels` allows (ViewChannel, Connect, SendMessages) must be in `BOT_PERMISSIONS`. "Mit Discord synchronisieren" (`createScheduledEvent`) needs CreateEvents. Discussion threads need CreatePublicThreads (and SendMessagesInThreads). A bot invited with an older URL lacks Connect, CreateEvents or CreatePublicThreads → re-invite with the logged URL or grant them to the bot role in the server settings.
- Gateway intents: Guilds, **GuildMembers (privileged — enable "Server Members Intent" in the developer portal)**, GuildMessages, DirectMessages, GuildScheduledEvents.
- The bot's role must be above `assignRoleId` roles to assign them.

## Approval requests (B-06)

With a Freigabe-Kanal chosen in the bot center (`approvalChannel`, no env variable), every registration that becomes `pending` (new registration in a manual event, `registerUserForEvent`; moving up into a manual event, `announcePromotions`) gets a request message there (`sendApprovalRequest`, fire and forget). „Annehmen“, „Ablehnen“, „Warteliste“ are allowed only for admins at the click (interaction roles contain `DISCORD_ADMIN_ROLE_ID`, or `memberPermissions` has „Administrator“; `hasAdminRole`) and run `changeRegistrationStatus` (`utils/registrationStatus.js`) like the website. The message is closed (`closeApprovalRequest`: no buttons, grey, result line) by every decision — Discord, website single action (inside the service), bulk action — and when the member withdraws (`unregisterUserFromEvent`), the event is cancelled or deleted (single and series, `closePendingRequests` in `utils/approvalRequests.js`). Without a channel or while the bot is offline nothing is posted; requests are never re-posted later. Events that end or get archived keep their open messages.

## Check-in invitations (B-07)

When an event with check-in (admin generated a code: `checkinEnabled` + `checkinCode`) has started and is not over, every accepted participant who is neither checked in nor invited gets one DM with „Einchecken“ (`event_checkin:<eventId>`) and „Zum Event“ — from the reminder scheduler (merged with the start DM into one message for members who get both) or right away when `generate-checkin` runs during the event (`sendCheckinInvitations`). It ignores the start switch and the „Erinnerungen“ choice; `checkinInvitedAt` on the registration (written before the DM) makes it at most once, also across new codes. The DM never contains the code. A click runs `checkInMember({ requireRunning: true })` (`utils/checkin.js`): "✅ Du bist eingecheckt!" + `checkinMessage`, "ℹ️ Du bist bereits eingecheckt." and "⌛ Der Check-in für dieses Event ist vorbei." edit the DM (button gone, link stays); not active / deleted, check-in off and no accepted registration answer privately. The website code stays as alternative.

## Comment ↔ thread sync (B-16)

Opt-in with `DISCORD_THREAD_SYNC=true` (then the client requests the privileged *Message Content* intent, see [configuration](../ops/configuration.md)). Only events with a `discordThread` (B-14) are mirrored; nothing is backfilled.

- Website → thread: `POST /api/events/:id/comments` saves the comment (`source: 'web'`) and calls `mirrorCommentToThread` fire and forget. The bot posts through its own webhook „DEMS Kommentare“ on the thread's parent channel (found or created on first use, kept only in memory, never stored) as „<Name> (Web)“ with the member's avatar, `allowedMentions: { parse: [] }` (no pings). Webhooks cannot send real replies, so a web reply starts with `-# ↪ Antwort an **<Name>**` and a jump link when the answered comment has a Discord message. The message id is stored as `discordMessageId`.
- Thread → website: `messageCreate` in an event's thread becomes a comment with the member's display name and avatar, `isAdmin` from `DISCORD_ADMIN_ROLE_ID` or the member's „Administrator“ permission, `source: 'discord'`, `discordMessageId`; mentions become `@name`/`#name`, custom emojis `:name:`, attachments one URL line each, cut to 1000 characters (`formatDiscordContent`). Messages of bots and webhooks (also the bot's own) are ignored, so nothing loops. A Discord reply to a mirrored message becomes a reply to its top comment.
- Deleting: the website delete calls `deleteMirroredMessage` (webhook copy via the webhook, a member's message needs „Nachrichten verwalten“; refused → logged, the comment is deleted anyway); `messageDelete` of a mirrored message deletes its comment.
- Editing: `messageUpdate` of a member message updates its comment and sets `editedAt` (the page shows „(bearbeitet)“); the website has no editing.
- Offline gaps are not reconciled: what happens while the bot is offline stays on its side.

## Announcement buttons

Layout (`buildEventAnnouncement`, B-05): optional ping line, then a container with `accent_color` = `event.accentColor` (else `#8b5cf6`): banner (media gallery), "## 🎉 <title>" + description, facts (🗓️ Datum, 👥 Plätze, 🔓 Zugang, then ⏳ Warteliste, 🤔 Ersatzbank (tentative registrations, B-17), 🏷️ Kategorie, ⏰ deadlines when set), separator, one block per slot ("**🛡️ Tank 2/2 ✅**" + first five names), last row. While `canRegisterViaDiscord(event)` (active, neither over nor past its registration deadline, and form fits into a modal) each slot block is a section with its button beside it (`event_slot:<id>:<slotId>`, "(voll)" when full, still clickable) and a slotless event gets "Anmelden" (`event_register:<id>`) in the last row; an event with `allowTentative` also gets "Vielleicht" (`event_maybe:<id>`, secondary, 🤔) there, slot events too (B-17); "Zum Event" (link) is always last. The announcement shows "⏰ Anmeldung bis" / "⏰ Abmeldung bis" for the optional deadlines (W-03); once the registration deadline passes, the scheduler refreshes the stored announcements once so only "Zum Event" stays, and old buttons or modals answer "Die Anmeldung für dieses Event ist geschlossen.". The ephemeral slot status answer drops the switch button after the registration deadline and "Abmelden" after the unregister deadline. The admin dialog previews this via `renderAnnounceButtonsPreview` (`public/js/admin/event-actions.js`).

## Gotchas

- Without `DISCORD_BOT_TOKEN` the web app runs, but every Discord helper is a no-op (`isReady` false).
- Every event link in announcements, buttons, DMs and `{event.url}` comes from `buildEventUrl` (`utils/eventUrl.js`) and opens `#event/<id>`. Messages sent before v2.5.1 still contain `#events/<id>`; the SPA router rewrites those.
- Announcements sent before 2.6.0 have no stored message ID and stay static. Announcements sent before B-05 are embeds; their next refresh converts them (their old text becomes the stored ping line).
