# bot.js and bot/ — Discord bot and Discord helpers

> TL;DR: `bot.js` (~80 lines) is the only entry point of the Discord bot: it wires the client and exports 48 helpers the routes call (DMs, channel messages, roles, guild data, event channels, scheduled events, bot status/settings). The code lives in 20 area modules in `bot/` (each ≤ 500 lines, readable whole): pick the module from the table below. Every helper returns `false`/`[]`/`null` while the bot is not ready. Split from one 3076-line file by B-01.

## Modules

`bot.js` is the only door: server, routes, utils and dev code `require('./bot')`, never a file in `bot/`. The modules in `bot/` require each other directly (never `../bot`), so calls between them use the real functions even in mock mode. `test/botModules.test.js` checks both rules, the size limits, that only `bot/client.js` creates a `Client`, and the export list.

Slash commands (`bot/commands.js`, guild-scoped, registered on ready): `/events` (list active events with the places sentence, public reply), `/register event:<autocomplete>` (B-03: same checks and messages as the "Anmelden" button; event without slots → registration modal or registered at once; slot event → private answer "Wähle deine Rolle für **…**:" with the `event_slot:` buttons of the announcement, ≤5 per row, so a click continues in `handleEventSlotButton`; form too big for a modal → link to the event page), `/unregister event:<autocomplete>` (deletes the registration, removes role, promotes waitlist). `/my-events` (B-04, no options: private overview of the own upcoming registrations with status, slot, „Abmelden“ (asks first; hidden after the unregister deadline and when rejected), „Slot wechseln“ (slot events with a held slot while registration is open) and „Zum Event“; the confirmation and the slot choice are classic messages because `handleSlotLeaveButton`/`handleSlotSwitchButton` answer with `content`, which a V2 message refuses). German clients see `/anmelden`, `/abmelden` and `/meine-events` (`setNameLocalizations({ de })`); Discord still sends `commandName` `register`/`unregister`/`my-events`, so routing and autocomplete use the base names. Descriptions are German for every language.

At the end of `bot.js`: `if (IS_MOCK_MODE) Object.assign(module.exports, require('./dev/mockBot'))` — in dev mock mode every Discord-facing export is replaced by a logging simulation (see [dev-mock-mode](dev-mock-mode.md)). Pure logic (`parseTemplate`, `buildEventAnnouncement`, `buildPollMessage`, `buildAnnouncementIntro`, settings, running events, `stopBot`) stays real. `bot.js` requires `dev/mockMode` before any `bot/` module, so the mock environment is set before `firebaseAdmin.js` loads. Because all other bot tests run in mock mode, `test/botRealExports.test.js` loads `bot.js` without it and pins the real helpers' neutral values while not ready.

## Rules for changes

- New Discord helper → into the module of its area (or a new `bot/<area>.js`), exported through `bot.js`, pinned in `test/botModules.test.js`, twin in `dev/mockBot.js` (otherwise mock mode calls the real, not ready function). Steps: [add-bot-feature](../howto/add-bot-feature.md).
- Guard every new Discord call with `if (!state.isReady) return <neutral value>;` and `try/catch` + `console.error` — routes must keep working without a bot.
- Use `flags: MessageFlags.Ephemeral` (not the deprecated `ephemeral: true`) and `Events.ClientReady`.
- Modal limits: max 5 top-level components (the intro text display counts; slot events with more than one slot use one for the `alt_slots` select → `getModalFieldLimit`), label ≤45, description/placeholder ≤100 chars.
- Calls between `bot/` modules (e.g. `checkReminders` → `sendDM`) use the real function even in mock mode.
- Requires of `utils/registrationService`, `utils/eventUtils`, `utils/pollStore` and `utils/announcementRefresh` stay inside functions: those utils require `bot.js` at load time.

## Gotchas

- Banners (W-12): `buildEventAnnouncement` and `createScheduledEvent` go through `bannerForDiscord` (`utils/bannerStore.js`). An external URL is passed on as is; an uploaded banner becomes `BASE_URL` + path in the announcement's media gallery (Discord fetches it, so it needs a public `BASE_URL` — with localhost the announcement shows no image) and the file itself for the scheduled event cover (works without a public URL). A missing file means no image. No new Discord call, so `dev/mockBot.js` has no twin for it.
- `sendChannelMessage` returns `{ channelId, messageId, guildId }` (it used to return `true`).
- Components V2 (B-05): a V2 message has no `content` and no `embeds`, at most 40 components counted with nesting (10 slots = 38) and 4000 characters over all text displays (the description gets what is left, `fitText`); a section needs an accessory, so slot blocks without a button (registration closed) are plain text displays. The ping line is a text display above the container; mentions in it notify per `allowedMentions`.
- Each announcement record stores its rendered ping line `intro`; `editStoredMessages` builds one payload per record and edits with `content: null`, `embeds: []`, `allowedMentions: { parse: [] }` (no second ping). A record without `intro` (posted before B-05) takes `message.content` as intro and the same edit turns the old embed message into the V2 layout; when Discord refuses, the record stays unchanged and the error is logged. Refreshes write the records back when one was dropped or converted (`recordsChanged`).
- `slot_switch`, `slot_leave` and `/unregister` call `deferUpdate`/`deferReply` first and answer with `editReply` — their side effects can exceed Discord's 3 s limit. A guest decline promotes the waitlist after answering.
- Event links come from `buildEventUrl` in `utils/eventUrl.js` (`#event/<id>`); a hand-built `#events/<id>` would open the event list — see [utils](utils.md). `test/eventUrl.test.js` scans `bot.js` and `bot/`.
